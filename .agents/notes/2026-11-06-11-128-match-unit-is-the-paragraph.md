# 决策：11-128 的判定单元是整段，改写要整段替换并配重试

状态：生效
日期：2026-11-06

## 问题

渠道校验族（CN 的 `400 / 11-128`）从 2026-10 起被当成「提示词里某句话是敏感词」处理：
`src/protocol/client.ts` 维护一张逐句对译表，每条 issue 往里加一行。结果是修完一轮又复发一轮
（#13 → #17 → #19 → #20 → #26 → #28 → #29 → #30），每轮都「部分有效」。

## 决策

1. **判定单元是整段，不是句子。** `@` 路径段落整段替换（`FILE_REFERENCE_PARAGRAPH`），
   保留 `@` 字形与 `@"..."` 形式 —— 模型仍要知道 `@` 的含义，只有网关读的措辞消失。
2. **11-128 族加有界重试**（400 ms / 1200 ms，可中断）。同一个 body 分钟级内会从 200 翻到 400，
   内容一致而结论相反，重试是唯一不依赖猜测的处置。
3. **判据用拒绝率，不用单次观测。** 三次以上、间隔六秒，与中性对照比。

## 实测（2026-11-06，CN 网关，真实 92 KB 会话）

| 形态 | 被拒 |
| --- | --- |
| 中性对照 | 0/6 |
| 真实 body 原样 | 6/6 |
| 去掉 69 个工具 | 仍拒 |
| 只留最近两轮历史 | 仍拒 |
| `system` 换成一句中性话 | 0/3 |
| 整段内**单句各自** | 200 |
| **整段** | 400 |
| 首句插一个 `that`（同族另一实现的方案） | 3/3 仍拒 |
| **整段替换** | **0/3** |
| 整段删除 | 0/3 |

段二分把元凶定在第 7 段（`@` 路径段落，407 字符）。

## 替代方案（试过、为什么不行）

- **逐句对译**（0.5.5 及更早）：`from` 串与宿主实发文本对不上，抓包段落过一遍
  `prepareChatBody` 逐字节不变 —— 改写从未命中。
- **插一个 `that`**（`mmqz/cpa-multi-plugins` 0.9.81 的方案，测于 2026-10-27）：
  在 11-06 的网关上是 3/3 被拒。判定单元在那两周内从「前两句」升级成了「整段」。
- **重写第二句**（把 `working directory` 改成 `workspace root`）：反而制造了签名的一半。
- **零宽字符**：网关先归一化再比对，等价于没改（#26 已退役）。
- **加身份头 / 换版本 / 换账号**：token 指纹一致、UA 一致，两者都不是变量。
- **只加抓包不改逻辑**：抓包只证明「不是内容」，能让方向从猜测转为实测，但不修复。

## 影响

- 用户可见：`@` 语义与 `@"..."` 保留；被拒的请求不再直接失败。
- 代价：真正的拦截会多等 1.6 秒才报错；`user` / `tool` 仍逐字节不动（那是事实依据）。
- 排障工具：抓包与宿主内重放见 [src/llm/README.md](../../src/llm/README.md)，
  判定方法与实测表见本记录。

## 遗留

为什么网关会分钟级翻转仍未确定（可能是灰度或短窗状态）；我们不据此做承诺，
只把重试当作兜底。
